        the API spec file, and the traceability viewer shows an incomplete picture.

  WRONG: story l2_sources omits the API endpoint ref
    l2_sources: ["SRS::MFU-001::S5::EVENT-001", "SRS::MFU-001::S3::txtSalary"]
    ← API endpoint SRS::MFU-001::API::PUT_... is missing → APISpec file absent from evidence

  CORRECT: story l2_sources includes all function refs AND AC refs

      "SRS::MFU-001::S5::EVENT-001",           ← functions[FN1].l2_source_ref

DIRECTIVE 3 — STORY VALIDITY DEFINITION & FUNCTIONS CEILING (ReAct: Reason)

  ── PART A: STORY COUNT — ONE STORY PER DISTINCT USER GOAL ──────────────────────
  The functions[] array is the evidence-based story CEILING (upper bound) — it is NOT
  a target to minimise. Each function entry represents one distinct S.5 event or
  coherent operation group.
  RULES:
    1. DEFAULT — cover EVERY distinct user goal: write one story for each function that
       represents an independently distinct workflow, up to {FUNCTIONS_CEILING} stories.
       Do NOT merge distinct user goals together just to reduce the count. Under-coverage
       (e.g. 2 stories when 5 functions have 5 distinct Happy Paths) is a DEFECT, just as
       over-production beyond the ceiling is.
    2. Collapse two or more functions into ONE story ONLY when they are genuinely the
       SAME Happy-Path workflow (e.g. "search" + "display results"). The Collision Test
       in PART A.1 is the decision rule: if two functions could EACH produce an
       independently distinct Happy Path, they MUST remain SEPARATE stories. Collapsing
       is the EXCEPTION for true variants — it is NOT the default and NOT a goal in itself.
    3. You MUST NOT split one function into two or more stories. One function = at most one story.
    4. If functions[] is empty (is_infrastructure=true or no events), return [].
    5. Reference the function's l2_source_ref in your story's l2_sources.

  ── PART A.1: HAPPY PATH COLLISION-AVOIDANCE RULE (CRITICAL — Gate 5) ──────────
  Each story MUST have EXACTLY ONE Happy Path AC (AC with path_type="Happy Path").
  A story with two Happy Paths means two DISTINCT workflows were incorrectly merged
  into a single story — this is ALWAYS a structural defect.

  COLLISION TEST — Before collapsing two functions into one story, answer:
    "Could both functions each produce an independently distinct Happy Path scenario?"
    • If YES  → they MUST become SEPARATE stories.
    • If NO   → they may be collapsed (they are variants of the same success path).

  DISTINCTION SIGNAL — Two functions have INDEPENDENTLY DISTINCT Happy Paths when:
    (a) They serve different primary user intents (e.g. "open a child screen" vs "open a system dialog")
    (b) Their success paths produce different types of visible system responses
        (e.g. "workspace renders new screen" vs "OS print dialog appears")
    (c) A developer could ship one without the other and each would be independently
        testable in isolation

  CORRECT collapse (SAME Happy Path workflow):
    FN: "Dispatch navigation to lab operations screens"
    FN: "Dispatch navigation to master data screens"
    → SAME pattern: user selects menu → screen opens. One Happy Path covers both.
    → Collapse into one story: "Navigate from Main Menu to Operations and Master Screens"

  WRONG collapse (DISTINCT Happy Paths — DEFECT-1 pattern):
    FN: "Dispatch navigation to child windows from menu"   → Happy Path: screen opens in workspace
    FN: "Open application preferences and printer setup"   → Happy Path: OS print dialog appears
    → These are DISTINCT workflows with distinct success outcomes.
    → MUST be SEPARATE stories. Collapsing them creates a Gate 5 two-Happy-Path failure.

  ── PART B: FOUR-CONDITION STORY VALIDITY TEST ─────────────────────────────────
  Before writing any story, apply this test. A candidate is a valid User Story if and only
  if ALL FOUR conditions are met. If any condition fails, the candidate MUST be collapsed
  into an Acceptance Criterion of a qualifying story — it CANNOT stand alone.

  CONDITION 1 — STATE CHANGE OR DECISION POINT:
    The story must result in either:
      (a) A data state change: record created, updated, deleted, session opened/closed,
          file written, batch job submitted, or status flag changed.
      (b) A user-visible decision outcome: validation result displayed, search results
          rendered, computed value shown, routing branch taken, authorisation granted/denied.
    FAIL examples (must become ACs):
      ✗ "Navigate to the stock management screen" — no state change, no decision point
      ✗ "Display the login form" — rendering with no outcome
      ✗ "Close the window" — no state change with business value

  CONDITION 2 — SINGLE USER INTENT:
    All operations described in the story serve ONE user goal achievable in ONE continuous
    interaction. If a user would naturally pause, navigate away, or context-switch between
    two operations, they are two stories.
    FAIL examples (must be split):
      ✗ "Search for a stock item AND update its quantity AND print the report" — three intents
      ✗ "Log in AND configure department settings" — two separate user sessions

  CONDITION 3 — INDEPENDENT DELIVERY VALUE:
    A developer must be able to ship this story to production without shipping any other
    story from the same feature. If the story is only meaningful or testable in conjunction
    with another story, it is an Acceptance Criterion of that story.
    FAIL examples (must become ACs):
      ✗ "Display error message when login fails" — this is AC2 of the Authenticate story
      ✗ "Show empty-result message when search returns zero rows" — this is AC3 of the Search story
      ✗ "Clear password field after failed login" — this is a Then clause, not a story

  CONDITION 4 — NON-COLLAPSIBLE:
    The operation cannot be fully expressed as a single Gherkin Given/When/Then step within
    a larger story's AC without losing coverage of a distinct user-visible outcome.
    If it can be an AC, it MUST be an AC.
    FAIL examples (must become ACs):
      ✗ "Validate member code format before submission" — this is AC2 of the Authenticate story
      ✗ "Auto-populate department name from member code lookup" — this is a Then clause
      ✗ "Display spinner during backend call" — purely UI feedback, not an outcome

DIRECTIVE 4 — STORY SIZING RULES (ReAct: Reason — INVEST Principles)
  * Story Points: Fibonacci ONLY — 2, 3, 5, 8. NEVER 1, NEVER 13+.
  * MINIMUM 3 points per story. A story scoring below 3 points has failed Condition 3 or 4 —
    collapse it into an AC of a qualifying story.
    Exception: a genuinely simple read-only display story with a backend query may be 2 points.
  * Size heuristic:
    - 2 pt: Simple read-only display (single field or label populated from one backend query, no mutation).
    - 3 pt: Single-action operation: one button → one DB query or API call → result displayed.
    - 5 pt: Multi-step workflow: input → validate → backend call → display result → handle errors.
    - 8 pt: Complex integration: multi-API orchestration, COBOL bridge, print/export pipeline,
            async batch trigger with status feedback, multi-phase transaction.
  * If a story exceeds 8 points, SPLIT it into two stories — but only if each half independently
    passes all four conditions in Directive 3.

  ⚠️  USER-FACING COMPLEXITY RULE (MANDATORY — prevents over-sizing):

  Story points reflect the USER'S interaction complexity — NOT the backend implementation
  complexity. Backend engineering complexity belongs in technical_notes and NFRs.

  SIZING PRINCIPLE: Ask "How complex is the USER'S experience?" — not "How complex is the code?"

  ANTI-PATTERN — over-sizing a simple trigger story:
    WRONG: A story where the user clicks ONE button to trigger a backend batch job scores 8 pts
           because the backend involves SQL, file I/O, and error logging.
           ← 8 points requires the USER to perform multiple distinct interactions, not just 1 click.

  CORRECT SIZING for trigger-style stories:
    Single-trigger with batch backend (one button → one async job):
      → 5 pt — the user provides input, triggers, receives feedback and handles error messages.
         The backend complexity is captured in technical_notes and NFRs; it does NOT inflate
         the user story's complexity score.
    Single-trigger with no input required (one click, no parameters):
      → 3 pt — purely mechanical action with a single outcome.

  8 pt IS JUSTIFIED ONLY WHEN:
    * The user interacts with 2+ distinct screens or steps within ONE continuous workflow, OR
    * The story requires the user to configure, approve, or monitor a multi-phase process, OR
    * The feature bridges to an external system that the user must explicitly navigate
      (e.g., user submits to COBOL batch, monitors job status, then retrieves results).

DIRECTIVE 6 — ACCEPTANCE CRITERIA RULES (ReAct: Reason)
Every story MUST have AT MINIMUM 3 ACs (1 Happy + at least 1 Negative + at least 1 Edge), but
3 is the FLOOR, not the target. EXACTLY ONE Happy Path per story, but you SHOULD add MULTIPLE
Negative Path and/or Edge Case ACs whenever the SRS describes more than one distinct failure
mode or boundary condition — cover each distinct validation rule, error branch, and boundary as
its own AC rather than collapsing them into one. (Multiple Negative/Edge ACs are encouraged and
pass the critic; only the Happy Path is capped at one.)
  * AC1: Happy Path (exactly one) — normal successful flow including expected system response.
  * AC2..: Negative Path (one per distinct invalid input / backend error / authorisation failure /
         constraint violation described in the SRS).
  * AC3..: Edge Case (one per distinct boundary: empty result set, concurrent edit, hidden control
         activation, zero-record response, session timeout, max-length, etc.).

  Gherkin format is MANDATORY: Given / When / Then.
  * "given" describes the pre-condition state (user state, data state, system state).
  * "when" describes the specific user action or system trigger (name the control if applicable).
  * "then" describes the observable outcome (UI change, data state change, system message).

  The l2_source_ref in each AC must point to the SPECIFIC L2 ID in the SRS that specifies that behaviour.

  ⚠️  GHERKIN IMPLEMENTATION CONTAMINATION GUARD (MANDATORY — applies to ALL three clauses):

  The "when" clause describes ONLY the observable USER ACTION — a button click, form submit,
  menu selection, or keypress. It MUST NOT describe internal system mechanics OR a system-internal
  event. This applies to Negative Path and Edge Case ACs TOO: the "when" is STILL a user action —
  put the failure/boundary condition in the "given" (pre-condition) and the failure result in the
  "then". NEVER make a system failure the "when".
    ✗ WRONG: when the OLE automation raises an error / when the API call times out /
             when the validation engine returns a negative code / when the search completes
    ✓ RIGHT: given the export component is unavailable, WHEN the user clicks the Excel button,
             then an error message '...' is shown and no file is produced.

  FORBIDDEN in "when":
    × SQL statements or fragments:
        "when the system executes 'SELECT emp_id FROM hr_employees WHERE is_active = 1'"
        "when the query SELECT * FROM hr_payroll runs"
        "when EXEC SQL SELECT MEMBER-CODE INTO WS-MEMBER END-EXEC"  (COBOL)
        "when EXEC CICS READ FILE('EMPFILE') INTO WS-EMP-RECORD"  (COBOL CICS)
    × Internal method/function calls:
        "when clsEmployee.UpdateSalary() is called"
        "when modDatabase.ExecuteBatch executes"
        "when the DataWindow retrieves via rs.Open"
    × File I/O or OS-level operations:
        "when the system writes to C:\HR\Exports\ACH_<month>.txt"
        "when CreateObject('Excel.Application') instantiates"
    × Backend processing steps that the user cannot observe:
        "when the system calls BeginTrans/CommitTrans"
        "when the COBOL paragraph PROC-PARA executes"

  CORRECT "when" examples (user-observable actions only):
    ✓ "when the user clicks the 'Run EOM Batch' button"
    ✓ "when the user submits the login form with their credentials"
    ✓ "when the user clicks the 'Generate Excel' button"
    ✓ "when the user clicks the Execute button"
    ✓ "when the user clicks the Update (更新) button with valid data in the grid"
    ✓ "when the user clicks the Delete (削除) button on the selected row"
    ✓ "when the user clicks the Save button after editing the master record"

  ⚠️  CRITICAL CONFUSION POINT — Update/Save and Delete buttons vs SQL operations:
  Japanese CRUD screens almost always have a button labelled "Update" (更新, cb_update)
  or "Delete" (削除, cb_delete). These are USER INTERFACE ACTIONS — a button click — NOT
  SQL DML operations. Apply this distinction strictly:

    CORRECT — the button click is the "when":
      ✓ "when the user clicks the Update (更新) button"
      ✓ "when the user clicks the Delete button on the selected master record"
      ✓ "when the user confirms the deletion dialog"

    WRONG — internal system operation leaked into "when":
      ✗ "when the system executes an Update on the master table"
      ✗ "when the record is Updated in the database"
      ✗ "when Delete is executed for the selected row"
      ✗ "when the DataWindow Update() method is called"

  The database UPDATE/DELETE is the RESULT of the user's click — it belongs in "then"
  or in "technical_notes". NEVER put it in "when". The "when" is always the physical
  button click or form submission the user performs.

  RULE: If the "when" content belongs in "technical_notes" (it describes HOW the system works
  internally), move it there. The "when" must describe WHAT the user does.

  ⚠️  L2 SOURCE REF VALIDITY GUARD (MANDATORY):

  SYNTHETIC REST SLUG PROHIBITION:
    FORBIDDEN: l2_source_ref values that use fabricated REST-path slugs as identifiers.
      These are auto-generated module-path slugs, NOT real SRS section anchors:
      INVALID: "SRS::MFU-003::API::POST_mod-frmbatchrun-mfu-003"
               ← "POST_mod-frmbatchrun-mfu-003" is a module-path slug, not an SRS anchor
      INVALID: "SRS::MFU-001::API::GET_mod-shared-mfu-001-employees"
               ← fabricated slug — no real SRS section has this identifier
    REPAIR: When the SRS has no S5::EVENT anchors (API-only MFU), use the nearest available
      ref from the feature's l2_sources[] — typically a S3 control ref or the best S5 ref present.
      VALID: "SRS::MFU-003::S3::txtMonth"   ← real control ref from S.3 table
      VALID: "SRS::MFU-003::S5::EVENT-001"  ← real S5 event anchor

  TRACE ID PROHIBITION:
    FORBIDDEN: l2_source_ref values that use TRCE-* trace IDs as section identifiers.
      Trace IDs (TRCE-UI-*, TRCE-IO-*, TRCE-WIN-*, TRCE-COM-*, TRCE-LOGIC-*) are source
      code line references, NOT SRS section anchors — they cannot be resolved to a viewer section.
      INVALID: "SRS::MFU-005::S5::TRCE-UI-frmreportviewer-L8"
               ← TRCE-UI-frmreportviewer-L8 is a code line trace, not an SRS section
      REPAIR: Replace with the containing S5::SPEC or S5::EVENT ref, or the nearest S3 control ref.
      VALID: "SRS::MFU-005::S5::SPEC-001"   ← the operational spec containing the trace
      VALID: "SRS::MFU-005::S3::DataGrid1"  ← the control being traced to

  ⚠️  GAP:: MARKER (for Negative Path / Edge Case ACs with NO error anchor):
    When a Negative Path or Edge Case AC has NO suitable error/failure event, boundary event,
    or control ref available for its l2_source_ref (e.g. a simple batch driver or a program the
    SRS documents as having no error handling), DO NOT force a success/happy-path event and DO
    NOT invent one. Use a GAP:: marker instead:
      VALID: "GAP::{mfu_id}::NO_ERROR_ANCHOR"          ← no error event exists for this scenario
      VALID: "GAP::{mfu_id}::NO_VALIDATION_IN_SOURCE"  ← the legacy code performs no validation
    Format: ^GAP::[\w-]+::\w+ . A GAP:: ref is a first-class, VALID l2_source_ref for Negative
    Path and Edge Case ACs — it documents an intentional SRS coverage gap and is accepted by the
    QA critic. Prefer a real error/boundary/control ref when one exists; use GAP:: only when none
    does. NEVER put a GAP:: ref on a Happy Path AC.

  ⚠️  AC DIFFERENTIATION RULE (MANDATORY — enterprise traceability requirement):

  Each acceptance criterion MUST reference the MOST SPECIFIC L2 ID for its own behaviour.
  FORBIDDEN: All three ACs (Happy Path, Negative Path, Edge Case) sharing the same l2_source_ref.
    This pattern signals that the story has NOT been traced — every AC pointing to the same
    single event means the error handling, boundary conditions, and validation rules have no
    distinct SRS source, which breaks traceability for auditing and testing.

  REQUIRED MAPPING — derive a distinct l2_source_ref for each AC:
    Happy Path AC  → the primary SRS section that describes the successful outcome:
                     S5::EVENT-NNN (the trigger event), API::POST_path (the endpoint),
                     or BATCH::STEP-NNN (the batch step).

    Negative Path AC → the SRS section that describes error handling, failure modes,
                       or constraint violations. Look for:
                       * Error response tables in API specs (HTTP 4xx/5xx rows)
                       * S.4 validation rules (S4::VAL-NNN)
                       * Error handling sections in BatchSpec (business_rules with error signals)
                       * S.3 error display controls (e.g., lblError, MsgBox sections)
                       If no dedicated error section exists, use the nearest S.3 control
                       that surfaces the error (e.g., the button that triggers the error path).

    Edge Case AC   → the SRS section that describes boundary behaviour, empty-result handling,
                     or the specific control/parameter that triggers the edge condition. Look for:
                     * S.4 boundary validation rules
                     * S.3 input controls that have range/format constraints
                     * API response handling for empty result sets (HTTP 204, empty array)
                     * BatchSpec job_steps with conditional logic

  EXCEPTION — single-source MFUs:
    When the ENTIRE MFU has exactly ONE SRS section (e.g., a minimal UIBlueprint with only
    one S.5 event and no error tables), it is ACCEPTABLE for all ACs to reference the same
    l2_source_ref. You MUST explicitly note this in the story's technical_notes:
    "Single SRS source — all ACs reference EVENT-001 as no separate error or boundary sections exist."
