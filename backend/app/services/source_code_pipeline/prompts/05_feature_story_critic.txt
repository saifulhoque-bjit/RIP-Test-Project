      * SRS says "No server-side operations; no data retrieval" but AC's given states
        "given no records exist in the database" -- the SRS explicitly negates the
        existence of any database query.
      * SRS says "Hardcoded title; no parameters read from source" but AC states
        "given batch parameters are missing" -- the SRS negates the existence of
        configurable parameters.
      * SRS says "Always succeeds; no error path" but AC is a Negative Path scenario.

  Do NOT fail on absence of detail (AC contains more specificity than the SRS).
  Only fail when the SRS EXPLICITLY NEGATES the AC's premise -- not when it is merely silent.

  FAIL message: "Gate 9a FAIL: {story_id} AC {ac_id} -- AC's given/when asserts
    [{AC premise}] but l2_source_ref {l2_id} contains explicit negation: [{SRS quote}].
    The AC's premise cannot be derived from this evidence. Replace the AC scenario
    or update l2_source_ref to evidence that supports this path."
  FAILED_STORY_IDS: include the story ID.

  ── 9b. Negative-Path Evidence Alignment ─────────────────────────────────────────
  For every AC with path_type = "Negative Path" OR path_type = "Edge Case":

  Step 1: Resolve the SRS event/step named in "l2_source_ref" from {SRS_CONTENT}.
  Step 2: Read the event's name, heading, and description text.
  Step 3: Determine whether the event is a SUCCESS/COMPLETION event or an
          ERROR/FAILURE event, using these signals:

    SUCCESS/COMPLETION signals (event is a happy-path outcome):
      Keywords in event name or description: "complete", "completion", "success",
      "successful", "notification", "notify", "generated", "output", "done",
      "result", "produced", "sent", "confirmed", "logged" (in a success context).

    ERROR/FAILURE signals (event is an appropriate anchor for a negative-path AC):
      Keywords: "fail", "failure", "error", "exception", "invalid", "timeout",
      "reject", "not found", "unavailable", "abort", "rollback", "missing",
      "exceeded", "denied", "unauthorised", "unauthorized".

    NAVIGATION / KEY-PRESS / BOUNDARY / PAGING signals (ALSO valid negative/edge anchors —
    these are alternate-flow events, NOT happy-path completion, and the deterministic pipeline
    classifier treats them as valid anchors for Negative Path / Edge Case ACs):
      "guard", "boundary", "top of page", "bottom of page", "first page", "last page",
      "no more", "beyond", "end of file", "end of list", "end of data", "out of range",
      "overflow", "underflow", a function/AID key ("PF3", "PA1", "AID", "XCTL",
      "transfer control"), "back", "cancel", "escape", "return to previous/prior",
      "navigate", or any key-press. An event carrying ANY of these signals is a VALID
      anchor for a Negative Path or Edge Case AC — do NOT fail Gate 9b for it, and do NOT
      classify it as a success/completion event even if it also contains a verb like
      "navigate", "display", or "open".

  FAIL if ALL of the following are true simultaneously:
    (i)  The AC has path_type = "Negative Path" OR "Edge Case".
    (ii) The AC's "when" or "then" describes a failure, error, timeout, or
         exceptional condition (e.g., "database fails", "connection timeout",
         "invalid input", "insufficient permissions").
    (iii) The resolved SRS event/step is a SUCCESS/COMPLETION event -- its heading
          and description contain success signals and NO error/failure signals.

  FAIL message: "Gate 9b FAIL: {story_id} AC {ac_id} -- Negative Path AC references
    success/completion event {l2_id} ('[event heading]'). A failure scenario must
    reference an error, exception, or validation-failure event. Suggested replacement:
    identify the closest error-handling event from the SRS (e.g. an event whose
    description mentions failure, timeout, or exception handling)."
  FAILED_STORY_IDS: include the story ID.

  PASS (do not flag) cases:
    * AC is Happy Path -- Gate 9b does not apply.
    * The referenced event has BOTH success and failure content (mixed description) --
      do not fail; the LLM chose a reasonable anchor.
    * l2_source_ref is a S3:: control ref or S4:: validation rule -- these are always
      appropriate anchors regardless of path_type; do not apply Gate 9b to them.
    * l2_source_ref matches ^GAP::[\w-]+::\w+ -- this is a STORY-SCOPED SRS-gap marker
      emitted by the deterministic normalizer when the story has no local error anchor.
      PASS Gate 9b UNCONDITIONALLY. Do NOT suggest replacing it with a success event such
      as S5::EVENT-001, and do NOT require any global "no error events" condition.
    * {SRS_CONTENT} not provided -- skip Gate 9b and note the omission.
