DIRECTIVE 2a — MIXED-TRACK MFU FUNCTIONAL PRECEDENCE RULE (ReAct: Reason)
A Mixed-Track MFU is one whose SRS covers heterogeneous artifact types: one or more
user-facing artifacts (login forms, data entry screens, search panels, workflow views)
co-packaged with system-level artifacts (MDI frames, menu shells, NVOs, session routers,
Win32 bridges).
This directive governs category and is_infrastructure classification
when both artifact types are present in the same MFU.

  MANDATORY FUNCTIONAL OVERRIDE TRIGGERS (any single trigger is sufficient to classify Functional):

    T1 — AUTHENTICATION ENTRY POINT
         Any SRS document within the MFU describes a screen that accepts end-user
         credential input: login field, password field, member code, PIN, or any
         session-establishment workflow (e.g. w_login, frmLogin, LoginDlg,
         SECMNG-driven login panel, OpenChannel initialisation driven by user input).

    T2 — DATA ENTRY FORM
         Any SRS document describes a panel, form, or dialog where the end user
         directly enters, selects, or modifies structured business data fields
         (text inputs, dropdown selects, date pickers, numeric entry, checkboxes,
         radio buttons).
         Presence of ANY I-flag control in S.3 satisfies T2.

    T3 — SEARCH / FILTER / RETRIEVAL INTERFACE
         Any SRS document describes a search form, filter bar, or retrieval panel
         where the end user supplies query parameters and receives business data
         records in response (DataWindow population, grid refresh, table binding).

    T4 — CRUD WORKFLOW
         Any SRS document's S.5 events include one or more of: record creation,
         record update, record deletion, or data retrieval driven by explicit
         end-user action (button click, menu selection, keyboard shortcut).

    T5 — USER-VISIBLE STATE CHANGE
         Any SRS document's S.5 events produce output directly visible to the end
         user: confirmation message boxes, error dialogs, data grid population,
         field value binding, or navigation to a result or detail screen.

  CLASSIFICATION OUTCOME:
    ► IF ANY trigger T1–T5 is satisfied:
        category = "Functional"
        is_infrastructure = false
    ► The co-presence of infrastructure artifacts (MDI frame, menu shell, NVO
      utility, session router, Win32 wrapper) does NOT override Functional
      classification.
      Infrastructure co-artifacts are documented in condensation_note.
    ► Classify as Infrastructure ONLY IF the entire MFU — every SRS document,
      every S.5 event, every S.3 control — is exclusively system-level with
      zero triggers T1–T5 satisfied.

  PRECEDENCE EXAMPLES (authoritative):
    MFU contains mdi_fact (MDI frame) AND w_login (login screen):
      → T1 satisfied → Functional. MDI frame goes in condensation_note.
    MFU contains menu_mdi_fact (menu dispatch shell) AND a data entry form:
      → T2/T3/T4 satisfied → Functional. Menu shell goes in condensation_note.
    MFU contains only iuo_Win32API + helper NVOs, no S.5 user events, no I-flag controls:
      → Zero triggers satisfied → Infrastructure. Legitimate.
    MFU contains mdi_fact whose S.5 events include OpenSheet calls that render
      user-facing child windows — the navigation itself is user-visible (T5):
      → T5 satisfied → Functional (Navigation/Dispatch category).
        Apply DIRECTIVE 8a Navigation/Dispatch grouping rule for functions[].

DIRECTIVE 3 — ONE FEATURE PER MFU (ReAct: Reason)
An MFU is defined as "a slice of the application that delivers one cohesive business outcome
or one technical orchestration path" (MFU System Policy v4.2).
Because each MFU encodes exactly one end-to-end workflow, the Feature Manifest for any non-infrastructure MFU MUST
contain EXACTLY ONE user-facing feature.

  MANDATORY RULES:
    1. Produce EXACTLY ONE user-facing feature per MFU.
       Never split one MFU into two or more user-facing features based on screen zones, toolbar positions, or control groupings.
    2. The single feature covers the ENTIRE MFU screen — all controls, all events, all validation rules.
       Use bounding_box.zone_id = "FULL_SCREEN" and bounding_box.screen_position = "full".
    3. If the SRS contains a mix of user-facing logic AND infrastructure artifacts (e.g. an
       NVO is bundled with a UI screen), produce ONE user-facing feature that covers the
       user-facing content only.
       The infrastructure content must be described only in the
       feature's condensation_note — do NOT create a second infrastructure feature alongside
       a user-facing feature.
       Exception: A fully infrastructure-only MFU (no user-facing content at all) produces
       a SINGLE infrastructure feature (is_infrastructure=true, functions=[]) with no
       user-facing feature alongside it.
    4. API Contract SRS: the entire endpoint group is ONE feature.
    5. Batch Blueprint SRS: the entire pipeline (OPEN -> PROCESS -> CLOSE) is ONE feature.

  ANTI-PATTERN: Do NOT create "Export & Print" or "Conditional Operations" as separate features.

DIRECTIVE 5 — ID GENERATION (ReAct: Reason)
Because each MFU produces exactly one user-facing feature, the feature ID always ends in F1:

  * MODULE_PREFIX: Strip the leading "MOD-" from module_id. Preserve ALL remaining segments
    exactly as-is — including short single-word identifiers.
    Examples: MOD-APP-LABO-STOCK -> APP-LABO-STOCK   (compound name, hyphens preserved)
              MOD-ANCES          -> ANCES             (short proper noun, no hyphens)
              MOD-IRAIDEN        -> IRAIDEN           (short proper noun, no hyphens)
              MOD-MASTER         -> MASTER            (single word — still strip MOD-)
              MOD-FUNC           -> FUNC              (single word — still strip MOD-)
              MOD-COMMON         -> COMMON            (single word — still strip MOD-)

    ⚠️  DO NOT retain the "MOD-" prefix — always strip it, regardless of whether the
    remaining segment is a short or single-word identifier.
    WRONG: MOD-MASTER → MOD-MASTER-001-F1   (retains MOD- prefix — INCORRECT)
    RIGHT: MOD-MASTER → MASTER-001-F1       (strips MOD- — CORRECT)
  * MFU_SEQ: USE THE INJECTED VALUE from the INPUT PAYLOAD field "MFU_SEQ" — do NOT re-derive it.
    The pipeline pre-computes MFU_SEQ using a collision-safe algorithm that handles non-standard
    MFU IDs (SYS-DEAD-01, SYS-UTIL-01, SYS-ALERT-01, etc.) that do NOT follow the MFU-NNN pattern.
    Re-deriving the sequence from the mfu_id string WILL produce collisions for non-standard IDs.

    ⚠️  NON-STANDARD ID COLLISION GUARD (CRITICAL):
    Standard IDs (MFU-001, MFU-002) map straightforwardly: MFU-001 → 001.
    Non-standard IDs (SYS-DEAD-01, SYS-UTIL-01, SYS-ALERT-01) do NOT — they are assigned
    hash-derived sequences in the 900–998 range to guarantee global uniqueness.
    ALWAYS copy the injected MFU_SEQ value. Never default to "001" for any non-standard ID.
    WRONG: SYS-DEAD-01 → "FRMBATCHRUN-001-F1"  ← collides with MFU-001's feature
    CORRECT: SYS-DEAD-01 → "FRMBATCHRUN-{injected_MFU_SEQ}-F1"  ← globally unique

  * Feature ID for the user-facing feature: {MODULE_PREFIX}-{MFU_SEQ}-F1
    Examples: APP-LABO-STOCK-001-F1, APP-LABO-STOCK-002-F1, ANCES-001-F1
  * Infrastructure feature (if MFU is entirely infrastructure): {MODULE_PREFIX}-{MFU_SEQ}-F1
    (still F1 -- there is only ever one feature per MFU regardless of type)
  * Function IDs: {FEATURE_ID}-FN{N} where N is a sequential integer starting from 1.
    Examples: APP-LABO-STOCK-001-F1-FN1, APP-LABO-STOCK-001-F1-FN2

DIRECTIVE 6 — L2 SECTION ID FORMAT (ReAct: Reason)
Use these canonical patterns — DO NOT deviate:
  * S.3 Control Row:      "SRS::{mfu_id}::S3::{control_name}"
  * S.4 Validation Rule:  "SRS::{mfu_id}::S4::{rule_id}"
  * S.5 Event:            "SRS::{mfu_id}::S5::EVENT-{NNN}"
  * S.5 Operational Spec: "SRS::{mfu_id}::S5::SPEC-{NNN}"
  * API Endpoint:         "SRS::{mfu_id}::API::{METHOD}_{path_slug}"
  * Batch Step:           "SRS::{mfu_id}::BATCH::STEP-{NNN}"

  ⚠️  API PATH SLUG GENERATION RULES (MANDATORY — prevents Gate 1 failures):
    path_slug = the endpoint path with ALL of the following transformations applied:
      1. Remove the leading slash
      2. Replace every remaining slash (/) with an underscore (_)
      3. STRIP CURLY BRACES from REST path parameters — keep the name, remove the braces:
           {employeeId}  →  employeeId
           {orderId}     →  orderId
      4. The result must contain ONLY characters matching [\w.-] (letters, digits, _, -, .)

    WORKED EXAMPLES:
      POST /api/v1/payroll/export                  →  POST_api_v1_payroll_export          ✅
      PUT  /api/v1/employees/{employeeId}/salary   →  PUT_api_v1_employees_employeeId_salary  ✅
      GET  /api/v1/orders/{orderId}/items          →  GET_api_v1_orders_orderId_items     ✅
      DELETE /api/v1/records/{id}                  →  DELETE_api_v1_records_id            ✅

    WRONG — curly braces (causes Gate 1 FAIL):
      PUT_api_v1_employees_{employeeId}_salary   ← curly braces are FORBIDDEN in L2 IDs

    ⚠️  INVENTED SLUG PROHIBITION (MANDATORY — prevents genuine Gate 5h FAIL):
    The path_slug MUST be derived from the ACTUAL endpoint path in the SRS
    (look for "Modern Endpoint Route:" or similar in the API spec document).
    It MUST NOT be a short descriptive label you invent.

    WRONG — invented descriptive labels (no api/v1 prefix):
      POST_payslip_generate                ← invented label, not a REST path
      POST_run_payroll_approval_001        ← invented with version suffix
      GET_employee_report                  ← invented label
    CORRECT — always starts with api_v{N}_ after HTTP method:
      POST_api_v1_payroll_payslips         ← derived from POST /api/v1/payroll/payslips
      POST_api_v1_payroll_approval         ← derived from POST /api/v1/payroll/approval
      GET_api_v1_reports_employees         ← derived from GET /api/v1/reports/employees

    RULE: If you cannot find a stated Modern Endpoint Route in the SRS, construct
    a canonical path following: /api/v1/{resource-plural}/{sub-resource}
    Example: payslip generation for payroll → /api/v1/payroll/payslips
             → POST_api_v1_payroll_payslips ✅

  ⚠️  TRCE-to-EVENT CANONICAL MAPPING (MANDATORY — prevents Gate 5h failures):
  Some SRS documents use TRCE-style trace IDs in S.5 descriptions instead of
  standard "S.5 Event #N" headers (e.g., modmain.bas, utility modules).
  When this occurs, you MUST map trace IDs to canonical EVENT IDs:

    Rule: Assign sequential S5::EVENT-NNN IDs to TRCE-based S.5 operations:
      First distinct S.5 operation/trace  →  SRS::{mfu_id}::S5::EVENT-001
      Second distinct S.5 operation/trace →  SRS::{mfu_id}::S5::EVENT-002
      (continue sequentially)

    Record the TRCE ID in the function's label or in the feature's condensation_note
    for developer reference, but use S5::EVENT-NNN as the L2 ID.

    WRONG:
      l2_source_ref: "SRS::MFU-006::S5::TRCE-UI-modmain-L14"
      ← TRCE IDs in L2 refs violate Gate 5h — they are NOT SRS section anchors
    CORRECT:
      l2_source_ref: "SRS::MFU-006::S5::EVENT-001"
      function label: "Initialise database connection and launch login form (TRCE-UI-modmain-L14)"
      ← canonical EVENT ID + trace ID preserved in human-readable label

  ASCII SLUGIFICATION RULE (MANDATORY):
    L2 IDs must be ASCII-safe.
    The regex pattern enforced by the critic is:
      ^SRS::[\w-]+::(S[1-5]|API|BATCH|S5)::[\w.-]+$
    where \w matches ONLY ASCII characters [A-Za-z0-9_].
    If a control name, menu item label, or rule ID contains non-ASCII characters
    (Japanese hiragana/katakana/kanji, Korean, Chinese, etc.), you MUST transliterate
    or replace them with an English ASCII slug before using them in any L2 ID.
    Slugification rules:
      1. Translate the meaning to English (preferred for clarity).
         Example: 'm_printer_settings'  (from Japanese printer settings control)
         Example: 'm_lot_correction'    (from Japanese lot correction control)
         Example: 'cb_new_registration' (from Japanese new registration button)
      2. If translation is uncertain, use the variable's programming name (e.g. cb_1, m_menuitem_3).
      3. Replace all spaces with underscores. Remove special characters.
      4. NEVER use raw Japanese, Chinese, Korean, or other non-ASCII text in an L2 ID.
    The human-readable name should be preserved in the feature description or title,
    NOT in the L2 ID itself.
