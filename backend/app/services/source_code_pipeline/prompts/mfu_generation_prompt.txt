## CRITICAL JSON STRING SAFETY RULE

When writing the `rationale` field, you MUST paraphrase SQL and code content
in plain prose.  Do NOT copy raw SQL identifiers, table names, column names,
or code tokens verbatim into the rationale string.

CORRECT — prose description:
  "masked_regions contain a SELECT MAX query (2,483 chars, start=6766) against
   an inventory master table using the FATRA transaction wrapper."

INCORRECT — raw SQL copied into string (WILL BREAK JSON):
  "SELECT MAX(M_DEVZAIKOIO.FIELD) FROM SIL00.M_DEVZAIKOIO USING FATRA..."

Rationale: raw identifiers like `M_DEVZAIKOIO` or schema-qualified names
like `"SIL00"."M_VOLAZUDEN"` contain characters that can corrupt JSON string
encoding.  You MUST describe the logic in natural language instead.
Use the `masked_region_count`, `char_count`, `start`/`end` offsets, and
`type` metadata provided to convey the same forensic evidence safely.

## Rationale Requirements (strengthened)

Rationale must reference:
* Specific artifacts and their **bubbled-up signals**.
* **Proprietary Business Logic:** You must explicitly cite the extracted logic found in `landmine_details.masked_regions` (e.g., specific SQL tables accessed, transaction commands) to justify the functional capability of the MFU.
* **AST Spatial Topology:** You must explicitly cite the `edges` array to justify structural boundaries and why grouping makes architectural sense.
* **External Dependency Impact:** If `external_dependency` is TRUE, the rationale must explicitly explain the architectural risk.
* Graph logic (traceability_chain, calls)
* Any uncertainty explicitly

Rationale should be auditable by a senior engineer.

Before producing JSON, verify:
* Each MFU represents a real user-meaningful capability or headless flow.
* No MFU is just a single technical component without feature context.
* Risk flags are grounded in evidence **and exist ONLY in this dynamically approved list: [{risk_flags}]**
* Rationale references concrete facts like `traceability_chain`, `edges`, and `masked_regions`.

Revise any MFU failing these checks before output.

## Infrastructure-Only Module Check (MANDATORY — run before output)

Scan the artifact payload for the following signals. If ALL of them are true,
you MUST return `{"mfus": []}` — an empty array is the CORRECT answer:

  ✓ SIGNAL 1 — No anchor artifacts: there is no `ui_anchor` or `batch_anchor`
    in the artifact list. Every artifact is `shared_logic`, `data_provider`, or `interface`.

  ✓ SIGNAL 2 — OS / system bridge only: artifacts contain exclusively Win32
    `Declare`/`DllImport` statements, kernel32/advapi32/user32 calls, global
    application constants (`Public Const`), or COBOL system-utility CALLs with
    no business SQL or EXEC CICS in `masked_regions`.

  ✓ SIGNAL 3 — No business SQL/CICS: `masked_regions` is empty, or contains
    only system-level calls (e.g., Sleep, GetUserName, RegOpenKey) with no
    domain data operations (no SELECT/INSERT/UPDATE against business tables,
    no EXEC CICS commands).

  ✓ SIGNAL 4 — Isolated cluster: `traceability_chain` contains only the
    artifact itself (no downstream business anchors reachable).

When ALL FOUR signals are present → return `{"mfus": []}`.

**This is not a failure.** The pipeline handles empty MFU lists gracefully:
the orphan sweeper will create a `SYS-UTIL` or `SYS-DEAD` bucket automatically.
Forcing an MFU for infrastructure-only artifacts produces low-quality, misleading
requirements that waste BA review time and pollute the modernization backlog.

Examples of artifacts that SHOULD produce `{"mfus": []}`:
  - `modWin32API.bas` — only Win32 Declare statements
  - `modGlobals.bas` — only Public Const declarations, no logic
  - `nvo_win32api.sru` — Win32 API NVO wrapper, no user operations
  - COBOL utility subprograms with no EXEC SQL or business data access

## Output Format (strict)

You must output only valid JSON matching the schema.
No prose outside JSON is permitted.

Structure:
```json
{
  "mfus": [
    {
      "id": "MFU-001",
      "name": "...",
      "description": "...",
      "execution_track": "MUST BE EXACTLY ONE OF: [{execution_tracks}]",
      "artifacts": ["..."],
      "traceability_chain": ["array", "of", "the", "primary", "anchor's", "path"],
      "complexity": "Simple | Medium | Complex | Critical",
      "risk_flags": ["MUST_MATCH_ALLOWED_LIST"],
      "ai_confidence": 0.95,
      "rationale": "Strong, fact-based architectural reasoning referencing AST edges and masked_regions."
    }
  ]
}
```

⚠️  CRITICAL — `ai_confidence` FIELD RULES (schema-enforced, pipeline will crash if violated):
1. `ai_confidence` MUST be a **standalone numeric JSON field** on EVERY MFU object.
   ✅ CORRECT:   `"ai_confidence": 0.86`
   ❌ FORBIDDEN: Writing "ai_confidence=0.86" or "estimated confidence is 0.86" INSIDE the `rationale` string.
2. `ai_confidence` MUST appear as its **own key** in the MFU JSON object — never embedded in any other field value.
3. Value MUST be a float between 0.0 and 1.0.  Do NOT write a percentage (86) — write 0.86.
4. The `rationale` field must NOT contain any confidence value or "ai_confidence" text.
   The numeric field is the SOLE authoritative record of your confidence score.
